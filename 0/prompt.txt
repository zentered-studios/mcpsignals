  ## 2. Tool call semantics (2026-07-28, `server/tools.mdx`, `schema/2026-07-28/schema.json`)
  - `tools/call` result: `{resultType, content[], structuredContent?, isError?}`. `structuredContent` validated against `outputSchema` if present; text mirror recommended for back-compat.
  - **Protocol errors** (unknown tool, malformed request) → JSON-RPC error, e.g. `-32602` Invalid Params. **Tool execution errors** (API failure, bad input) → `isError: true` in the result, not a protocol error — spec explicitly says this so the LLM can self-correct.
  - `ToolAnnotations` (all hints, untrusted from untrusted servers): `readOnlyHint` (default `false`), `destructiveHint` (default `true`, meaningful only when `readOnlyHint==false`), `idempotentHint` (default `false`), `openWorldHint` (default `true`), `title`.

  - `notifications/cancelled`: on stdio only now — on Streamable HTTP, closing the SSE response stream *is* the cancel signal; the notification is neither sent nor expected there.

  - Elicitation (`ElicitRequestFormParams`/`URLParams`, `ElicitResult{action: accept|decline|cancel, content?}`) still active; Sampling deprecated but schema retained. `notifications/elicitation/complete` and `elicitationId` (added in 2025-11-25) were **removed** in 2026-07-28 because MRTR replaces the correlation mechanism.
  - `icons`: `Icon{src, mimeType?, sizes?, theme?}`; strict security rules — HTTPS/`data:` only, same-origin, no credentials sent, reject `javascript:`/`file:` etc.
  - `title`/`BaseMetadata`: `{name, title?}`; `Tool.annotations.title` takes precedence over `name` for display.
  
  ## 3. Lifecycle (breaking change)
  - **No `initialize` handshake.** Every request must carry, in `_meta`: `io.modelcontextprotocol/protocolVersion` (required), `io.modelcontextprotocol/clientCapabilities` (required), `io.modelcontextprotocol/clientInfo` (optional, SHOULD send) — an `Implementation` object: `{name, title?, version, description?, icons?, websiteUrl?}` (all confirmed in `schema.json`). Servers SHOULD echo `io.modelcontextprotocol/serverInfo` in each result's `_meta`.
  - `Mcp-Session-Id` header: **removed**, no protocol-level sessions of any kind.
  - `MCP-Protocol-Version` header: still required on every Streamable HTTP POST, must equal the body's `_meta` protocol version or the server returns `400`/`HeaderMismatch` (`-32020`). Servers MAY treat a missing header as `2025-03-26` for legacy clients.
  - New required headers: `Mcp-Method` (every request) and `Mcp-Name` (`tools/call`/`resources/read`/`prompts/get`), mirroring body fields for intermediaries; plus opt-in `x-mcp-header`/`Mcp-Param-*` for individual tool params (spec explicitly warns **not** to use this for secrets/tokens/PII).

  ## 7. Logging/privacy guidance
  - `server/utilities/logging.mdx`: MUST NOT log credentials/secrets, PII, or internal details that could aid attacks; SHOULD rate-limit, sanitize sensitive data, validate fields.
  - `server/tools.mdx` Security Considerations: servers MUST validate inputs, rate-limit, sanitize outputs; clients SHOULD show tool inputs to the user before calling (anti-exfiltration) and log tool usage for audit.
  - `x-mcp-header` guidance: SHOULD NOT mark sensitive params (passwords, API keys, tokens, PII) — header values are visible to network intermediaries. Directly relevant to mcpsignals' arg-redaction feature.
  - `clientInfo`/`serverInfo` in `_meta` are self-reported, unverified by the protocol; spec says implementations SHOULD NOT use them for security decisions — worth documenting in mcpsignals as "informational only."
